Figma-first pipeline

Where the value goes

A design system only works if a decision you make once survives every tool it passes through. This is the route from a Figma comp to shipped code, and the checks that catch it when the route breaks.

Figma → Claude Design → Claude Code WCAG 2.1 AA Read time ~8 min

Follow one value

Here is a single colour making the trip. In the top row it is bound to a Figma Variable. In the bottom row someone typed the hex directly into the fill. Same colour, same comp, same designer — and only one of them arrives.

How a token value appears at each stage of the pipeline
Origin 1 · tokens.json 2 · Figma 3 · Handoff 4 · Code Gate
Bound to a Variable color.action.default color/action/default color/action/default var(--color-action-default) Passes
Typed in by hand color.action.default #0F5C8C · local style #0F5C8C #0F5C8C Build fails
The name is the payload. A hex code tells you what a thing looked like on one day. A token name tells you what the thing is — which is the only version of the information that can be rebranded, themed, contrast-checked, or reasoned about by anything downstream.

Before anything else

Your tokens must already be in Figma as Variables, synced from tokens.json. If the Figma styles were created by hand in Figma, stop here and fix that first. Everything below assumes one source of truth; with two, the rest of this guide is theatre.

PHASE 1

Design in Figma

Judgment lives here
01 Human

Sync the Variables before you start

Pull from tokens.json at the beginning of the session, not the end. A stale Figma file is more dangerous than no Figma file, because it still looks authoritative.

02 Human

Bind every value — no typed hex, no typed pixels

Fills, strokes, corner radii, gaps, text styles: all bound to Variables. This is the one decision that determines whether the rest of the workflow functions, because it is the difference between the two rows in the trace above.

If a design needs a value that has no token, that is a real finding. Add it to tokens.json and re-sync. Do not solve it locally.

03 Human

Use Auto Layout throughout

Not for tidiness. Auto Layout is the only way the file records intent — direction, spacing, alignment, and how things resize. A frame with absolutely positioned children exports as coordinates, which describes exactly one screen width and nothing else.

04 Human

Write down what the picture cannot hold

Two minutes in a text file. This is the difference between a specification and a decoration:

  • Every interactive state — hover, focus, active, disabled, error, loading, empty
  • Focus order and keyboard behaviour
  • What a screen reader should announce, and when
  • Breakpoint behaviour — what reflows, what stacks, what is removed
  • Which text is real content and which is placeholder
05 Human

Audit the comp before it leaves

Contrast on every text-and-background pairing. Touch targets at 44 px minimum. Fixing this here costs minutes; fixing it after code exists costs a cycle, and fixing it after launch costs a complaint.

PHASE 2

Pick a route

One question: is the design settled?
Path A

Figma → Claude Code

Take this route when the comp is settled and you are implementing a known thing.

  1. Connect Dev Mode MCP. Select the frame in Figma, then ask Claude Code for the design context of your current selection.

    Check what comes back. You want variable names. If you are seeing hex codes, the Variables are not bound — return to step 02. Do not work around it; the workaround is the drift.

  2. Hand over both artefacts. The Figma reference and the written notes from step 04. The notes are not optional — they are the half of the spec the image could not carry.
  3. Constrain the work explicitly before it starts, using the brief below.
  4. Read the diff, not the summary. A summary is a claim about the diff. The diff is the diff.
Path B

Figma → Claude Design → Claude Code

Take this route when the comp is a starting point and you expect to iterate — variants, breakpoints, states the static file never showed.

  1. Export the frame as PNG, plus the variable list as text. There is no native pipe between Figma and Claude Design. The text list is what keeps the token names alive across the gap.
  2. Iterate visually. Explore what a static file cannot show: the error state, the empty state, the 320 px version, the version where the heading runs to ninety characters.
  3. Run a drift check before you leave. Scan the output for any literal hex, px, or rem. It fails often enough that this is worth doing every single time.
  4. Carry forward the decisions, not the code. Describe what you settled on, then continue through Path A. The sketch resolved questions; the repo is where the real thing gets built, against real files, with real gates.
BRIEF Delegated

What to tell Claude Code before it starts

Keep this in a CLAUDE.md file at the root of the repo so you are not retyping it, and so it applies to everyone on the project.

## Tokens
Use only CSS custom properties from build/css/variables.css.
Reference semantic tokens (--color-action-*), never
primitives (--core-*).
If a value has no matching token, STOP and say so.
Do not introduce one.

## Scope
Implement every state listed in states.md, not just the default.
Do not modify tokens/*.json. Do not edit build/ output.

## Verification
Before reporting the work complete, run:
  npm run lint:tokens
  npm run test:a11y
Paste the actual output. Do not describe what the
commands would return.

That last instruction is doing more work than it looks like. Asked to confirm, a model will readily narrate plausible command output it never ran. Requiring the paste turns a claim back into evidence.

PHASE 3

Gates

Identical on both routes
06 Automated

Let the machine catch the mechanical failures

lint:tokens rejects any off-system colour, spacing, or type value. test:a11y catches contrast, missing accessible names, and heading structure. Both run from committed scripts, not from a command someone remembers.

Automated tooling reliably finds contrast, labelling, and structural problems. Published estimates of total WCAG coverage cluster somewhere between a third and a half, depending on the tool, the page, and how you count — treat any single figure with suspicion, including that one.

07 Human

Do the part that cannot be delegated

These four checks cover the criteria no linter reaches — focus order, meaningful sequence, and reflow:

  • Tab through the whole thing. Can you see where you are, always?
  • Screen reader on anything interactive. Does it announce what it does?
  • Resize to 320 px wide. Does anything scroll sideways?
  • Text zoom to 200%. Does anything clip or overlap?
08 Human

Compare back to the comp — for intent, not pixels

The question is not whether it matches. It is whether it reads the way the design meant it to read: same hierarchy, same emphasis, same thing catching the eye first.

REFERENCE

Who owns what

The split is not arbitrary, and it is worth being able to defend out loud: judgment stays where mistakes spread quietly and cost a lot to undo; execution is handed off where mistakes are local and immediately visible.

Stage Owner

What this does, and what it doesn't

None of this makes generated output correct. What it does is make unverified output expensive to ship: the linter blocks, the accessibility test fails, the manual checklist sits unticked. That is a smaller promise than "safe", and it is the one that holds up under questioning.

The residual risk is worth naming plainly. Every gate above filters a known failure class. A component that passes all of them and is still confusing to use remains entirely a human problem, and no amount of tooling changes that.
